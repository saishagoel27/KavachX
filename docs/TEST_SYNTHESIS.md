# Test synthesis

`candidate → TestSpec → validation → harness generator → sandbox → oracle → verdict`

Code: [`backend/app/testing/`](../backend/app/testing/)

```
              the model    Pydantic       KavachX          existing   KavachX
              proposes     enforces       generates        adapter    decides
                  ▲            ▲              ▲                ▲         ▲
candidate → TestSpec → validation → harness generator → sandbox → oracle → verdict
```

The requirement this implements is blunt: **the LLM must not be able to run arbitrary generated
commands.** A model can only influence execution by filling in fields of a `TestSpec`. It cannot
supply code, a command, an interpreter, a path or a flag — every one of those is either a constrained
enum, a workspace-relative path validated against the index, or generated by KavachX from its own
template.

---

## TestSpec

[`specs.py`](../backend/app/testing/specs.py)

```python
class TestSpec(StrictModel):
    target: str                    # symbol handle, shape-validated, no ".."
    entrypoint: str
    input_source: InputSource      # 7 values
    strategy: Strategy             # unit|property|fuzz|mutation|regression|differential
    oracle: OracleSpec             # 13 deterministic kinds
    expected_security_property: str
    timeout_ms: int                # 100 .. 600_000
    payloads: list[str]            # ≤64, each ≤8_000 chars, no newline/NUL
    property_expression: str       # single boolean expression, no statements
    fuzz: FuzzSpec | None
    request_template: dict
    payload_field: str
    cwe: str
    reproductions_required: int     # 1..10
```

The validators are enforcement, not documentation:

- `target` / `entrypoint` must match a symbol-handle shape and may not contain `..` — a traversal
  sequence in a *target* is not a test payload, it is an attempt to point the harness outside the
  workspace.
- payloads are size-capped, and a newline or NUL is **rejected** rather than escaped. Escaping is a
  judgement call; refusing is not. Multi-line input goes through `input_source="corpus_file"`, which
  has its own handling.
- `property_expression` must be a single expression with no statements and no `import`, and is then
  compiled by the **SAMHITA restricted-AST whitelist** — the same compiler that rejects calls,
  attribute access and subscripts — *before* a harness is generated.
- strategy coherence: `fuzz` needs a `fuzz` block, `property` needs an expression,
  `differential` needs the baseline-comparison oracle, and `unit`/`regression`/`mutation` need a
  payload **or** a request template to replay.

That last "or" was a fix. Requiring a payload rejected a valid regression spec for a genuinely
reproduced finding whose reproducing input was a whole request rather than a separable field —
costing the run its regression guard.

### What the model decides, and what it does not

| The model | KavachX |
| --- | --- |
| what to target | which engine runs |
| which inputs matter | the marker/canary values |
| which mutation families are valuable | the harness code |
| what property to assert | the argv |
| | the timeout ceiling |
| | the reproduction count |

The engine is chosen by KavachX because it is a function of the detected language and the toolchain
that is *actually installed*; letting a model pick would only produce specs naming engines that are
not present.

## Oracles

[`oracles.py`](../backend/app/testing/oracles.py) — 13 kinds, each a pure function of an
`ExecResult`:

```
exit_code_nonzero  exit_code_equals  crash_signal  sanitizer_report
exception_raised   assertion_failure  marker_in_stdout  canary_content_in_stdout
contract_violation  output_differs_from_baseline  timeout  resource_exhaustion  no_crash
```

There is deliberately **no** oracle that takes a natural-language description and decides whether
output "looks wrong". That is the judgement call this architecture exists to avoid making.

Three properties:

- **`UNSUPPORTED` is not `HELD`.** "The sanitizer output was not available" and "no sanitizer report
  was found" are different facts. Collapsing them into a negative is how a run reports a clean
  result it did not earn.
- **Marker values come from KavachX**, not from the spec. A model-chosen marker could collide with
  the target's own output and manufacture a reproduction that never happened.
- **`no_crash` is a real oracle**, used by differential replay and benign verification, where the
  property being asserted is "this behaves normally".

`require_reproductions()` enforces the standard the existing validator already holds itself to: one
firing can be a flake, a race, or an artefact of a shared workspace; N independent firings in
separate processes is a reproduction.

## Engines

[`engines.py`](../backend/app/testing/engines.py) — real frameworks, **probed** rather than assumed.

| Engine | Language | Strategies | Coverage feedback |
| --- | --- | --- | --- |
| `python-stdlib` | python | unit, regression, differential | — |
| `hypothesis` | python | property | — |
| `atheris` | python | fuzz | ✅ |
| `kx-mutational` | python | fuzz, mutation | ✅ |
| `libfuzzer` | c | fuzz | ✅ |
| `afl++` | c | fuzz | ✅ |
| `asan` / `ubsan` | c | unit, regression, fuzz | — |
| `fast-check` | javascript | property, fuzz | — |
| `vitest` | javascript | unit, regression, differential | — |
| `go-fuzz` | go | fuzz | (unimplemented) |
| `junit` | java | unit, regression | (unimplemented) |
| `cargo-fuzz` | rust | fuzz | (unimplemented) |

Three states, and the difference between them is the whole point:

- **available** — toolchain present, generator exists.
- **unavailable** — generator exists, toolchain missing, **missing pieces named**. The strategy is
  reported as **NOT RUN**, never as clean.
- **unimplemented** — KavachX has no generator for that (language, strategy) pair.

`go-fuzz` is marked unimplemented deliberately: a draft generator exists, but the harness needs a
package-level output-capture helper KavachX does not inject, so selecting it would produce a
guaranteed compile failure. Reporting it as unimplemented is honest; running it and reporting the
compile failure as a test result is not.

### The probe must run in the right process

`sandbox_module_checker()` / `async_module_checker()` probe **inside the sandbox**, because the
sandbox interpreter is what executes a harness.

This was a measured bug. `pytest` was importable in the backend process, so the engine was reported
available; the generated harness then died in the sandbox with

```
python: No module named pytest
```

and that surfaced downstream as *"the oracle did not fire"* — indistinguishable from a clean result,
against a target with a live, reproducible command injection.

Two fixes: probe the sandbox, and remove the dependency entirely — see below.

## Harness generation

[`harness.py`](../backend/app/testing/harness.py)

> **No string from a model ever becomes code.**

Every harness is produced from a KavachX-authored template. The spec contributes *values*, inserted
as data literals. A payload containing `"); os.system("rm -rf /` lands in the generated file as a
quoted string literal and stays data.

Every generated file carries a banner naming its plan id, target, strategy, oracle and property — so
it is identifiable in a diff, in an artifact listing, and if one is ever copied into a target
repository by accident.

### Two literal renderers, because JSON is not Python

```python
_py_lit(value)   # repr()      — Python literals
_js_lit(value)   # json.dumps  — JavaScript/JSON literals
```

JSON is *not* a subset of Python literal syntax: it renders booleans as `true`/`false` and null as
`null`. Using `json.dumps` for a Python harness produced generated files containing

```python
if true:
```

which died with `NameError: name 'true' is not defined` at the first line of execution — a whole
strategy silently failing to run, reported as "the oracle did not fire".

`_assert_plain()` guards both: `repr` of an unexpected object emits `<object at 0x…>`, which is a
syntax error in the generated file, so an unexpected type fails loudly at generation time.

### Two driving modes

| Mode | Used by | Why |
| --- | --- | --- |
| `subprocess` | mutation, fuzz, differential | Spawns the target as its own process and reads **real** process stdout. A vulnerable target can write to fd 1 from a shell it spawned, and `contextlib.redirect_stdout` only rebinds Python's `sys.stdout` — it would not see that at all. **Missing a signal is the one failure mode a prover must not have.** |
| `in_process` | unit, regression, property, atheris | Imports the entrypoint and calls it with an **argv list** — which is what the confirmed entrypoint takes (`main(argv)`), not a request dict. Idiomatic for a file a maintainer keeps. |

Calling `main(request_dict)` was the first version. argparse rejected it and the process exited 2,
so every generated test reported "did not reproduce".

### The unit/regression harness is dual-mode

It defines ordinary `test_*` functions **and** a `__main__` block that runs them with no pytest:

```python
if __name__ == "__main__":
    sys.exit(_run_all())
```

A maintainer who receives it alongside the patch runs it with their own pytest. KavachX runs it as
`python <file>`, so the most important strategy cannot be disabled by the sandbox image's package
list. Depending on a third-party runner for KavachX's own verification was the mistake.

### Verified

```
mutation    reproduced=True  count=2/2  attempts=2
  PROOF: marker_in_stdout: marker present in stdout — The marker appearing in stdout proves
         the injected command executed: nothing in the target's own output can produce it.
  attempt 0: exit=1 signals=[] oracle=FIRED
  attempt 1: exit=1 signals=[] oracle=FIRED
  coverage: measured=True pct=20.0
  env: dev network_enforced=False
```

The winning payload, recovered from the harness's own report:

```
kavachx-probe&echo KAVACHX_POV_MARKER_7F3A
```

## Execution

[`executor.py`](../backend/app/testing/executor.py)

- **The sandbox is entered through the existing adapter, unchanged.** No new execution path, no
  relaxed limits, no extra capability. If a harness needs something the sandbox denies, the harness
  does not run and that is recorded.
- **Reproductions are independent** — one `execute()` call, therefore one process, per attempt.
  Execution stops early only when the oracle did *not* fire, since the required consecutive
  reproductions can then no longer be reached.
- **The oracle decides**, and its verdict is recorded verbatim with the observable that decided it.

`TestExecution` records everything §30 asks for: the input hash, the environment (adapter, isolation
model, honest capability flags, limits), the commit SHA, the index id, the harness path **and its
hash**, the command, per-attempt exit codes, signals, stdout/stderr/output hashes, peak RAM, CPU
seconds, egress, the reproduction count, coverage, and any artifacts read back.

The environment's capability flags are in there because a reproduction recorded under the dev adapter
and one recorded under gVisor are not equally strong evidence, and a certificate has to be able to
tell them apart.

## Coverage-guided fuzzing

[`fuzzing.py`](../backend/app/testing/fuzzing.py), [`coverage.py`](../backend/app/testing/coverage.py)

```
seed corpus → execute → coverage → mutate → execute → new coverage?
                                              ├── yes → keep the input
                                              └── no  → discard it
```

Everything in the loop is deterministic. The model's role is bounded: every few rounds it receives
**coverage feedback** — newly reached lines, still-uncovered branches *with their source conditions*,
crashes so far — and proposes candidate inputs and mutation families. Those are then executed, and
**whether they were good is decided by whether coverage actually moved.**

That is the difference between LLM-guided and LLM-implemented fuzzing, and it is why a model
proposing nonsense costs a round rather than corrupting the campaign: a candidate that reaches
nothing new is discarded by the same rule that discards a random mutation that reaches nothing new.

`FuzzCampaign` records `model_candidates` alongside `model_candidates_useful` — the honest,
*measured* score for the model's contribution.

### Code-aware seeding

`uncovered_branches()` parses each unreached conditional and derives concrete values from the
literals it compares against. The spec's example exactly: if the uncovered branch is `if limit < 0:`,
the campaign tries `-1`, `0`, `1` — the boundary and both sides of it, the classic off-by-one triple
— rather than random bytes. A `len(x) > N` comparison yields `""`, `"x"`, `"x"*64`, `"x"*1024`.

Branch-derived values are queued **before** mutations, because a value taken from the literal an
uncovered `if` compares against is far more likely to flip that branch. Suggestions are hints for
the deterministic mutator; whether an input reaches the branch is decided by re-measuring coverage.

### Twelve mutation families

```
boundary_values  negative_numbers  large_values  empty_and_null  type_confusion
encoding_variants  separator_injection  traversal_sequences  length_escalation
unicode_edge_cases  format_specifiers  structural_nesting
```

The model may select families; it never supplies an operator, because an operator is code.

> The `unicode_edge_cases` operator is written with **source-level escapes**, never raw characters.
> A literal NUL byte made the whole module unparseable (`source code string cannot contain null
> bytes`) and took down the EXECUTE node at import time; a literal U+202E right-to-left override
> silently reorders the line for anyone reading the diff.

### Coverage as two different things

1. **A bound on assurance** — "39% of statements executed" is what stops a Level A certificate from
   being read as "this code is safe".
2. **A steering signal** — `new_relative_to()` decides whether an input is kept.

`unmeasured(reason)` returns an *explicit non-measurement* rather than an empty observation, so
downstream code cannot read "we did not measure" as "nothing was covered".

Coverage reuses the existing `kx_observe` tracer rather than adding a second instrumentation path:
two coverage numbers for one run that disagree would be worse than one number with stated limits.

## Regression tests

[`regression.py`](../backend/app/testing/regression.py)

When a finding is validated, the input that proved it is the most valuable artifact the run
produces: a *known* exploit against a *known* location with a *known* deterministic signal.

Two durable things:

1. **A regression `TestPlan`** the gauntlet re-runs against every patch iteration. A patch is not
   verified until the original exploit no longer fires.
2. **A test file in the target's own convention** — pytest, unittest or vitest, chosen from what the
   repository already uses — offered as a publishable artifact. If a maintainer applies the patch,
   they get the test that proves it works, in the framework they already have. That is the difference
   between a patch they must trust and one they can check.

The payload comes from the validator's recorded `pov_request` / `pov_payload`, never from anything
regenerated: a regression test built from a reconstructed input tests a guess about the exploit.

Two forms:

| Form | When | Shape |
| --- | --- | --- |
| **split** | the payload matches one request field | template + `payload_field` |
| **replay** | it does not | the whole recorded request *is* the test |

The replay form matters for findings whose reproducing input is not a single substitutable field — a
header block, a multi-field request, a fuzzer-supplied structure. Splitting those apart would either
drop the payload or invent a field name that does not exist.

### Regression specs are post-validation only

A pre-validation regression spec carries only the *benign* base value the mutation operators start
from, so it asserts nothing — it passes on the unpatched build, which is the opposite of what a
regression guard is for. Observed directly: the pre-validation regression harness reported `HELD`
against a target with a live command injection.

Verified post-validation, against the **unpatched** build:

```
regression plan: True
  harness: _kavachx/tests/kx_regression_ac0adbd38e68.py
  regression on UNPATCHED build: reproduced=True (1/1)
  PROOF: marker_in_stdout: marker present in stdout
  publishable artifact: tests/test_kavachx_regression_v01.py
```

Artifacts are written under `_kavachx/`, **not** into the target's `tests/`. The target tree is the
thing under analysis; dropping files into it would change the pinned artifact and pollute a diff
meant to contain only the patch. The publisher places them at their intended path when a pull request
is actually opened.

## The deterministic fallback

`deterministic_specs()` derives usable specs from a flow with **no model involved**, using a table
from sink class → oracle → request shape → mutation families.

This is the floor of the system's capability. A run with `LLM_PROVIDER=mock`, an unreachable model,
or a model returning schema-invalid output still generates and executes real, deterministically
judged security tests.

That is why this is not "LLM + grep + patch": remove the model entirely and the system still finds,
tests, validates and repairs. The model makes it better, not possible.

Model-proposed specs are **additive** and ordered *after* the deterministic ones, so if the
per-candidate cap bites, the test KavachX knows how to judge survives.

### Sinks that cannot be proved in a sealed sandbox

Stated on the plan, so the resulting evidence is never over-read:

| Sink | Why not |
| --- | --- |
| `sql` | No database in the sandbox — a SQL sink can be shown to crash or receive attacker-shaped input, not to execute injected SQL. |
| `network_request` | No network interface, so an SSRF sink cannot be shown to reach anything. |
| `auth_decision` | Proving a bypass needs a full request lifecycle the harness does not reconstruct. |
| `crypto` | A weak-primitive finding is a property of the code, not an observable runtime effect. |

## Deduplication

A `plan_id` is `sha256(canonical spec + index id)`, so two candidates yielding an identical spec
yield an identical plan id — and on the demo target they do: two flows reaching the same shell sink
produce the same target, strategy, oracle and payload.

That is not a collision to work around. It is the same test. Both synthesis and execution
deduplicate by `plan_id`, and the second candidate records that it *shares* a test rather than
generating another — executing it twice would waste a sandbox execution and double-count the
evidence.
